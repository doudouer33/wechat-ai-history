# 微信聊天记录实时增量同步开发计划

**基础项目：** [nanlis/wechat-ai-history](https://github.com/nanlis/wechat-ai-history)\
**当前分支：** `feat/incremental-sync`\
**目标平台：** Windows 10/11\
**目标微信版本：** 4.1.15.56

---

## 一、项目目的

基于现有 `wechat-ai-history` 项目，增加微信本地聊天数据库的实时增量同步能力，使项目能够持续获取微信中新增的聊天记录，而不需要反复执行全量解密。

现有项目已经具备微信数据库密钥提取、SQLCipher 数据库解密、聊天记录查询及 MCP 接入等功能，但目前主要依赖全量解密流程。

如果每隔几秒重新解密整个数据库，会造成大量不必要的 CPU 和磁盘 I/O 开销，无法满足实时读取的需求。

因此，本项目的核心任务是：

**在保留现有全量解密能力的基础上，实现可靠、高效的数据库增量同步，使现有聊天记录查询接口能够及时读取新增消息。**

### 最终目标

1. 首次运行时，可以通过现有方式完成数据库全量解密或初始化。
2. 后续能够持续检测微信数据库中的新增数据。
3. 正常运行时只处理发生变化的数据，不重复全量解密。
4. 能够正确处理 SQLite WAL、Checkpoint 和 WAL Reset 等情况。
5. 支持程序重启后的断点续读。
6. 保证增量同步的数据完整性和一致性。
7. 不影响现有聊天记录查询功能及 MCP 接口。
8. 对微信原始数据库保持只读。

## 二、开发范围

本项目围绕现有微信数据库读取能力，重点实现增量同步、异常恢复和现有查询功能兼容。

新增功能应尽量复用现有代码，保持模块独立性和通用性。

## 三、开发阶段

### Phase 1：现有项目验证与全量解密基准

**目的：** 确认现有项目在真实 Windows 微信环境中能够正常运行，并建立后续增量同步的正确性基准。

本阶段由 Codex 主导完成，不需要预先手动重复执行。

#### 1.1 项目代码与环境检查

- 阅读现有项目 README、架构文档和相关源码。
- 检查 Python 版本及项目依赖。
- 检查现有自动化测试。
- 运行现有测试，记录结果。
- 检查当前 Git 分支，确保在 `feat/incremental-sync` 上工作。
- 检查 `.gitignore`，确保敏感数据不会进入 Git。

重点关注现有的数据库密钥提取、全量解密、WAL 解析和消息查询实现。

#### 1.2 真实环境全量解密

在用户授权和必要的管理员权限下，使用现有项目提供的流程：

1. 确认 Windows 微信 4.1.15.56 正常运行并已登录。
2. 执行现有密钥提取流程。
3. 执行现有数据库全量解密流程。
4. 检查解密结果及数据库文件。

如果某个操作需要 UAC 授权、人工登录或其他交互，由 Codex 明确提示用户配合。

不要为了完成测试而绕过安全检查。

#### 1.3 解密结果验证

- 检查解密数据库是否能够正常打开。
- 执行 `PRAGMA integrity_check`。
- 检查数据库文件数量、大小及基本结构。
- 确认消息表和相关字段。
- 确认现有查询模块能够正常读取数据。

#### 1.4 现有查询功能验证

使用仓库现有接口：

- 列出聊天会话。
- 查找指定微信群。
- 读取指定群的历史消息。
- 验证消息发送者、时间戳和正文。
- 检查长文本消息是否能够完整读取。

#### 1.5 建立基准

记录以下非敏感信息：

- 数据库文件数量和大小。
- 相关数据库页大小。
- 消息表结构。
- 消息唯一标识字段。
- 全量解密耗时。
- 查询耗时。
- 目标数据库的基本状态。

不需要在测试报告中记录真实聊天内容或数据库密钥。

**本阶段测试与验收：**

- 现有自动化测试通过，或明确记录原有失败项。
- 真实微信数据库能够成功解密。
- 数据库完整性检查通过。
- 能够读取指定微信群的历史消息。
- 长文本消息能够正确读取。
- 获得可用于后续增量同步对比的基准数据。

**阶段交付：** 一份现有项目验证报告，包括环境、解密结果、查询结果、性能基准和已发现的问题。

如果现有项目本身存在问题，应先报告问题，不要直接大规模修改原有代码。

### Phase 2：增量同步方案分析与实现

**目的：** 在现有项目基础上，增加可靠的数据库增量同步能力。

本阶段是项目的核心。

具体技术路线暂不预设，进入本阶段前先进行专项技术分析。

#### 2.1 技术路线分析

需要重点研究：

- 能否使用 SQLCipher 只读连接直接访问微信正在运行的数据库。
- 能否正确读取主数据库及 WAL 中已经提交的新事务。
- SQLite Checkpoint 和 WAL Reset 对读取的影响。
- 现有 `decrypt_stream.py`、`wal_snapshot.py` 等代码能否支持增量解密。
- 是否存在更简单、更可靠的增量读取方式。

比较不同方案的：

- 实现难度。
- 数据正确性。
- 实时性。
- CPU 和磁盘 I/O 开销。
- 异常恢复能力。
- 与现有项目的兼容性。

先提交技术分析报告和实现计划，经用户确认后再开始编码。

#### 2.2 增量同步功能实现

根据确认后的技术路线，实现：

- 首次初始化。
- 持续检测新增数据库数据。
- 只处理新增或发生变化的内容。
- 正确识别已提交事务。
- 持久化同步状态。
- 支持断点续读。
- 避免重复处理。
- 支持异常恢复。

如果采用 WAL 增量解密方案，还需要正确处理：

- WAL Header 和 Frame。
- Checksum 校验。
- Commit Frame。
- 数据库页增量解密。
- Checkpoint。
- WAL Reset。
- 数据库文件变化。

如果采用 SQLCipher 直接读取方案，则应重点验证数据库连接、WAL 可见性、事务一致性和并发访问行为。

不应为了追求某一种实现形式而增加不必要的复杂度。

#### 2.3 异常恢复

需要考虑：

- 程序意外退出。
- 数据库文件发生变化。
- WAL 文件被删除或重新创建。
- Checkpoint。
- WAL Reset。
- 同步状态损坏。
- 数据库读取过程中发生并发写入。
- 增量同步结果与实际数据库不一致。

出现无法安全恢复的情况时，应能够回退到全量解密和重新初始化。

**全量解密应当作为首次初始化和异常恢复手段，而不是日常轮询方式。**

**本阶段测试：**

- 连续提交多次数据库事务。
- 测试单个事务修改多个数据库页。
- 测试未提交事务。
- 测试 Checkpoint。
- 测试 WAL Reset。
- 测试数据库重启和文件变化。
- 测试程序中途退出。
- 测试重新启动后的断点续读。
- 测试重复同步。
- 测试异常状态恢复。

**阶段交付：** 独立的增量同步模块、相关自动化测试及实现说明。

### Phase 3：正确性验证与现有功能集成

**目的：** 验证增量同步能够长期稳定运行，并确保不破坏现有项目功能。

#### 3.1 增量结果正确性验证

这是最重要的验收环节。

在测试过程中：

1. 通过微信产生新的聊天消息。
2. 等待增量同步程序处理。
3. 获取增量同步后的数据。
4. 使用全量解密重新生成一份基准数据。
5. 对比两者的查询结果。

要求：

- 已提交消息不丢失。
- 消息正文一致。
- 发送者和时间戳一致。
- 不存在重复消息。
- 数据库状态正确。

对比时应使用消息唯一标识及相关字段，不要仅依靠消息数量判断。

#### 3.2 现有功能兼容性

验证现有项目的：

- 聊天会话查询。
- 群聊历史消息查询。
- 消息搜索。
- MCP 接口。

均能够正确读取增量更新后的最新数据。

不得因为增加增量同步而破坏原有接口。

#### 3.3 实时性与资源占用

测量：

- 数据库新事务提交时间。
- 增量同步发现新数据的时间。
- 查询接口读取新消息的时间。
- 增量同步耗时。
- CPU 占用。
- 内存占用。
- 磁盘 I/O。

实时性目标：

- 支持 0.5～1 秒级的检测间隔（具体取决于最终技术路线）。
- 数据库提交后，正常情况下争取在 2 秒内让新增消息通过现有查询接口可见。
- 无新消息时保持较低资源占用。
- 正常运行不进行周期性全量解密。

以上为目标值，需要真实测试验证，不得将未经测试的数据作为实际性能结果。

#### 3.4 长期稳定性测试

- 连续接收多条微信消息。
- 测试多个数据库事务。
- 测试程序重启。
- 测试微信退出和重新登录。
- 测试 Windows 睡眠及唤醒后的恢复。
- 测试长时间运行。
- 检查内存是否持续增长。
- 检查是否存在漏消息或重复消息。

**本阶段测试与验收：**

- 增量结果与全量解密基准一致。
- 原有查询接口正常工作。
- WAL 相关异常能够正确处理。
- 程序重启后能够恢复。
- 实际同步延迟和资源占用有测试数据支撑。
- 长时间运行没有发现无法恢复的数据不一致问题。

**阶段交付：** 完整测试报告、性能数据、使用说明和最终代码。

## 四、总体技术要求

1. 优先复用现有项目代码。
2. 保留现有全量解密功能。
3. 不修改微信原始加密数据库。
4. 正常运行不重复执行全量解密。
5. 以正确性和可靠性优先于性能优化。
6. 使用持久化状态支持断点续读。
7. 对新增代码编写自动化测试。
8. 不为了实现增量同步而大规模重构无关模块。
9. 保持现有 Python 接口、查询功能和 MCP 兼容性。
10. 所有技术选型必须有测试或实际运行结果支撑。

## 五、安全与 Git 管理要求

- 所有数据库密钥仅在本地使用。
- 不上传微信密钥。
- 不上传解密后的数据库。
- 不上传真实聊天记录。
- 不在日志中输出密钥或完整聊天正文。
- 完善 `.gitignore`。
- 测试数据使用人工生成的样本。
- 不修改微信原始数据库。
- 不自动向上游提交 PR。
- 开发始终在 `feat/incremental-sync` 分支进行。

提交代码前检查 Git 变更，确保不存在敏感数据。

## 六、最终验收标准

当前仓库完成后，应当满足：

1. 现有全量解密功能正常。
2. 能够持续获取微信数据库中的新增数据。
3. 正常运行不需要周期性全量解密。
4. 能够正确处理 WAL 和 Checkpoint 等情况，或由选定的替代技术路线提供等价保证。
5. 程序重启后能够恢复同步。
6. 已提交消息不丢失、不重复。
7. 增量同步后的数据能够被现有查询接口读取。
8. 不破坏现有 MCP 和其他读取功能。
9. 有真实环境下的实时性和资源占用测试结果。
10. 能够长期运行并处理异常。

**项目核心原则：只解决微信聊天数据库的可靠增量读取问题。先验证现有功能，再确定技术路线，最后实现和测试增量同步。**
