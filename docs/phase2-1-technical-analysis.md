# Phase 2.1：实时增量读取技术路线分析

日期：2026-11-01，Asia/Tokyo（UTC+09:00）。仓库基线：`c433dda`，分支：`feat/incremental-sync`。真实环境：Windows 11 x64、Python 3.12.4、微信 4.1.15.56。

## 1. 推荐结论与需要确认的取舍

**推荐路线 A：Windows 使用原生 SQLCipher 只读连接，直接查询微信主库及已提交 WAL；由数据库引擎处理页读取、锁、事务边界和 Checkpoint。** 保留现有全量解密流程与明文镜像，作为离线读取、独立比对和异常恢复工具。暂不建设自研 WAL 页复制器。

这已经有本机可行性证据：4 个在线消息分片成功只读打开；247 张消息表、84,028 条记录在同一批冻结快照上的全部字段比较无差异；用户向文件传输助手发送的合成测试文本，在主数据库副本尚无该记录时，已通过 SQLCipher 在线连接读到。

推荐理由是减少一致性职责，而不是追求新组件：路线 A 使用 SQLite 已有的读事务协议，避免自行维护 WAL 游标、Checkpoint 追赶、物理页发布与崩溃恢复。这符合“可靠读取新增聊天记录”的目标。

**请在 Phase 2.2 前确认以下边界：**

1. 实时接口将直接读加密源，`decrypted/` 保留为带时间点的离线镜像，**不承诺始终与源物理同步**。如果要求其他程序继续用普通 SQLite 读取一个持续更新的完整明文镜像，路线 A 单独不能满足，必须重新讨论镜像需求。
2. 源 `.db` 与 `-wal` 不执行数据写入、不主动 Checkpoint、不迁移或改密钥；正常 SQLite 读取仍可能参与 `-shm` 锁协调，缺失时还可能创建辅助文件。**若要求源目录包括 SHM 在内绝对零写入，当前直读路线尚未满足该要求**，应先在隔离副本上验证权限受限的读法，失败时停止在线直读。
3. “重启后恢复读取”与“逐条事件恰好消费一次”是不同能力。原计划没有指定消费目标。本报告建议先实现可靠的当前状态读取及持久化来源/恢复状态，不默认建设消息队列或逐行复制系统；若需要持久化的新增消息消费游标，须同时确认其输出目标和更新/删除语义。

本阶段只增加本报告、合成实验脚本和文档索引。没有修改核心模块或运行依赖清单，没有实现持续增量同步；Phase 2.2 仍等待用户确认技术路线。

## 3. SQLCipher 只读直连：可行性与正确设置

### 3.1 Windows 上实际可运行

**R：** 实验使用 `sqlcipher3==0.6.4` 的 CPython 3.12 Windows x64 wheel，单独安装到 `.local/phase2_1/vendor/`，未加入项目依赖。该包是 Python 绑定维护者发布的二进制分发，不是声称来自微信或 Zetetic 商业支持的组件。[绑定项目](https://github.com/coleifer/sqlcipher3)、[固定版本发行页](https://pypi.org/project/sqlcipher3/0.6.4/)。

| 项目 | 实测值 |
|---|---|
| wheel | `sqlcipher3-0.6.4-cp312-cp312-win_amd64.whl` |
| wheel SHA-256 | `ff612c1f731a1870457a3fa4c0095bf27ce13ad7e2035ec3f98a489e2d6ccf5c` |
| `PRAGMA cipher_version` | `4.19.0 community` |
| 引擎 SQLite 版本 | `3.53.4`，不是 Python 标准库的 3.45.3 |
| 编译选项 | 含 `HAS_CODEC`、`THREADSAFE=1`、`USE_URI`、`TEMP_STORE=2` |
| 在线源连接 | `mode=ro`、`uri=True`、`query_only=ON`；无 `immutable`、`nolock` |

应检查实际 `cipher_version` 和查询结果，不能把普通 SQLite 对未知 PRAGMA 的静默忽略当成 SQLCipher 已启用。[SQLite PRAGMA 规则](https://www.sqlite.org/pragma.html)。生产依赖选型仍要固定版本、校验 wheel、核对许可证并在受支持 Python/Windows 组合上回归；一次本机安装不是支持矩阵。

### 3.2 区分账号密钥与 SQLCipher raw encryption key

**R+C：** 仓库文件里的 32 字节账号密钥记为 `K_account`，每库首页前 16 字节为 `salt`。本次成功连接使用：

```text
K_db = PBKDF2-HMAC-SHA512(K_account, salt, 256000, 32 bytes)
SQLCipher key = raw hexadecimal representation of K_db
cipher_compatibility = 4
```

设置发生在首次数据库内容读取前。SQLCipher 的 raw hex key 语法直接使用给定 32 字节加密密钥，不能直接用捕获的 `K_account` 冒充每库 `K_db`；也不能把其十六进制文本当成普通口令。HMAC 校验保持启用。[SQLCipher key API](https://www.zetetic.net/sqlcipher/sqlcipher-api/#PRAGMA_key)、[页加密设计](https://www.zetetic.net/sqlcipher/design/)。

现有 `crypto.derive_key()` 的派生公式可复用；其持久化派生密钥缓存不应被实验默认调用。推荐在进程内按账号密钥标识与 salt 缓存 `K_db`，来源或 salt 变化即失效。`db.preamble()` 关于 `kdf_iter=1` 的说明不准确：raw key 的不再派生来自 key 格式；之后 `cipher_compatibility=4` 又会恢复兼容参数。新连接初始化应明确顺序，不能照搬注释。

### 3.3 真实数据库比较

**R：** 从当前微信加密主库和 WAL 捕获冻结加密快照；同一份输入分别由 SQLCipher 和现有 `decrypt_all.decrypt_db()` 解密后读取。比较各 `Msg_*` 表按 `local_id` 排序的全部列，使用包含类型信息和记录长度的序列摘要；不是仅比较消息数量。

| 分片 | Msg 表数 | 冻结快照记录数 | 差异表数 |
|---|---:|---:|---:|
| `message_0.db` | 92 | 36,831 | 0 |
| `message_1.db` | 69 | 22,829 | 0 |
| `message_2.db` | 26 | 6,275 | 0 |
| `message_3.db` | 60 | 18,093 | 0 |
| 合计 | 247 | 84,028 | 0 |

4 个冻结消息库的 SQLCipher `integrity_check` 全部 `ok`。在线只读连接也成功读取全部 4 个分片的 schema 和 `Name2Id`，均为 WAL 模式，原有 `-wal`/`-shm` 存在。

另一次稳定元数据窗口内，在线结果与 WAL 合并快照的全部消息表摘要一致。**这一次的主库副本本身也已包含相同消息记录，单靠这一组比较不能证明新增 WAL 事务可见。** 因而另做了下面的新增消息实验。

### 3.4 真实已提交 WAL 可见性

**R：** 用户向自己的文件传输助手发送一条合成标记。只读连接在 `message_3.db` 的对应消息表读到该标记，紧接着复制的主库单文件副本中尚无该标记；源 WAL 文件存在，物理长度为 4,194,304 字节。

该观测直接支持“当前环境 SQLCipher 能读到已提交、尚未 Checkpoint 到主库的新消息”。实验没有通过工具向他人发消息，没有在源库执行写 SQL。

**H：** 本次没有取得微信真实事务的精确提交时间；消息时间戳只有秒级且探针启动晚于人工发送。因此不能把记录中的时间差当作提交到可见的延迟，更不能宣称已通过 2 秒延迟验收。真实微信 Checkpoint、WAL Reset 和登录重启的连续组合仍需后续验证。

### 3.5 只读的边界

**S+C：** `mode=ro` 约束数据库写访问，`query_only` 是额外约束。合成实验关闭 `query_only` 后，写 SQL 仍被 `mode=ro` 拒绝。但在可写的私人目录中，给定主库与 WAL、缺少 SHM 时，只读连接确实创建了 `-shm`；主库与 WAL 的哈希保持不变。SQLite 官方也规定了只读 WAL 连接与辅助文件的条件。[只读 WAL 数据库](https://www.sqlite.org/wal.html#read_only_databases)、[SHM 与文件生命周期](https://www.sqlite.org/walformat.html)。

`immutable=1` 会跳过锁和变化检测。合成实验中，它读到了旧值而正常连接读到新 WAL 值；它只用于已经冻结的实验副本，不能用于在线源。`nolock=1` 同样不是可靠的并发读取修复方案。[URI 参数定义](https://www.sqlite.org/uri.html#uri_query_string)。

## 4. 两种路线怎样保证一致性

### 4.1 路线 A：由 SQLCipher/SQLite 维护快照

**C：** 在单库短读事务内，SQLite 按已确定的 WAL 读边界读取页面；其他连接尚未提交的数据不应可见。事务结束后下一读事务再观察新提交。Checkpoint 与读事务通过引擎锁协调。[事务隔离](https://www.sqlite.org/isolation.html)、[WAL 读算法](https://www.sqlite.org/fileformat.html#reader_algorithm)。

**S：** 使用真正的 SQLCipher 加密合成库，写者和读者为独立连接：

| 场景 | 合成实测结果 |
|---|---|
| 大事务写入但未提交，WAL 已有 391,432 字节 | 只读连接仍看不到新记录 |
| 提交 100 条，主库哈希不变 | 只读连接读到 100 条，证明从 WAL 读取 |
| 读事务固定后，另一连接更新旧行并新增一行 | 原读事务保持旧值和 100 条记录 |
| 原读事务释放 | 下一事务读到新值与 101 条记录 |
| 老读事务仍在时请求 TRUNCATE | 返回 `[1,104,102]`，报告 busy，未强制截断 |
| 释放读事务后 TRUNCATE | 返回 `[0,0,0]`，WAL 归零，新数据仍可读 |
| RESTART 后再次写入 | WAL 前后均为 4152 字节，salts 已变，新数据可见 |
| 关闭并重开只读连接 | 可读当前最新状态，无需保存 WAL offset |

这些是可控制的同进程、多连接实验。**尚不是微信真实多进程、长时间运行或不同 WCDB 编译版本的压力认证。**

长读事务会拖延 Checkpoint 或 WAL 回收；应限制查询持锁时间，生成器提前退出时关闭游标和连接，大导出另行安排一致快照。`BUSY`/`LOCKED` 需要有界重试，不能假设 WAL 模式永不冲突。

一致性默认是**单数据库事务**。多个消息分片和联系人库不能自动获得全局同一时刻快照；两条路线都应保留逐库时间点和边界，不伪造跨库原子性。公共接口应维持现有结果形状，并在异常时明确失败或明确离线来源。[WAL 多库限制](https://www.sqlite.org/wal.html)。

版本门槛也应核实：SQLite 官方披露的 WAL-reset 并发写入/Checkpoint 缺陷已在 3.51.3 及部分回移版本修复；本次实验引擎为 3.53.4。不能据此推断微信内置引擎也包含修复，且本项目不会对源主动执行 Checkpoint。[官方缺陷说明](https://www.sqlite.org/wal.html#walreset)。

### 4.2 路线 B：自研 WAL 增量解密和明文物理镜像

**C：** 正确实现至少需要同时解决“源读取一致”和“目标发布一致”，不能只解密新增 frame：

1. 校验主库身份、账号、salt、页大小、WAL header、generation salts 和连续滚动 checksum；offset 必须绑定 generation，文件长度不等于有效帧终点。
2. 按完整事务暂存页面，到 commit 边界才应用；同一事务不能让查询者看到部分页。页 HMAC 与 WAL checksum 分别校验，前者不替代后者。
3. 正确处理事务中的增长、截断和重复页；截断后重新增长不能从旧主库恢复已删除页面。
4. 与 SQLite 读边界及 Checkpoint 锁协调。仅在文件中发现完整 commit frame，不等于已经证明与某个 SQLite 读事务的可见边界相同；必须分析 wal-index 发布、恢复规则和竞态，不能把这个推断当作已完成验证。
5. 在读新 frame 和再次读取其页内容之间防止 Reset 覆盖。应读入并验证同一批稳定数据，而不是先记录 offset，再逐帧重新打开源文件。
6. 在 Checkpoint 已回填、WAL 被截断/替换且未读帧消失时，能够判定连续性已丢失并重新初始化；不能从旧 offset 接着读或只从新 WAL 开始。
7. 在目标侧提供崩溃恢复与读者互斥：页集合、数据库大小和已应用位置要么一起提交，要么可完整回滚；不能先推进状态再写页。

SQLite 的 WAL 是可回收的数据库日志，**不是供外部消费者永久保留的消息队列**。如果同步进程离线期间新帧已被 Checkpoint/Reset 回收，单靠保存在本地的旧 WAL offset 无法恢复缺失页；回退全量是必要的安全路径。[WAL 文件格式与 Reset](https://www.sqlite.org/fileformat.html#walformat)。

目标发布尤其容易被低估：直接覆盖正在被普通 SQLite 读取的明文主库页，没有参与目标 pager 的事务协议，即使每页都正确也会暴露混合状态。每次完整复制再 rename 可简化发布，却会重新产生与整库大小相关的写入；自建 undo/redo、目标锁与恢复日志则显著增加复杂度。Windows 打开文件的替换行为还必须实测。当前仓库没有提供这些保证。

**H：** 路线 B 尚未有本阶段的完整增量原型、原子发布、崩溃恢复或真实微信并发证明。不能把现有全量解密成功当成这条增量路线已跑通。

## 5. 两条路线对比

令 D 为库大小、W 为保留 WAL 大小、F 为新帧数量、U 为新事务涉及的不同页数、Q 为查询实际访问页数。下表成本为源码/机制分析，不是完整同步器跑分。

| 维度 | A：SQLCipher 只读直读 | B：WAL 增量解密 + 明文镜像 |
|---|---|---|
| 核心一致性职责 | 引擎管理单库事务、锁与页可见性 | 自研帧解析、源快照、事务应用、目标发布和恢复 |
| 实现难度 | 中等：原生后端、发现与缓存失效、故障状态 | 高：除解析外还有物理镜像事务与崩溃协议 |
| 初始化 | 验证账号与 key，按需解密访问页；可后台预热 | 必须构建完整明文基准，通常 O(D) |
| 正常 CPU | 按需解密 Q 页及 SQL 执行；长搜索仍可能扫描全库 | 理想状态校验 F 帧、解密 U 页，另外仍有查询 CPU |
| 空闲开销 | 持久连接的 data_version 与目录发现可较轻 | 需要侦测新帧/Reset；长度或 mtime 单独都不够 |
| 正常磁盘读取 | 请求涉及页；页缓存可减少重复读取 | 至少读取新 WAL frame；Reset 追赶可能重读主库 |
| 正常磁盘写入 | 无明文镜像页写入；有独立状态和可能的 SHM 协调 | 明文页、恢复日志、状态持久化；发布策略可能引入 O(D) 复制 |
| 实时性 | 查询时读取已提交状态；通知可用 0.5–1 秒轮询 | 检测 + 完整事务捕获 + 目标提交后才可见 |
| Checkpoint/Reset | 重新建立读事务，通常不需要追日志位置 | 必须识别 generation；丢帧要全量恢复 |
| 重启恢复 | 重新验证身份与密钥、读取当前源；无物理同步进度 | 校验镜像与状态共同提交点，再验证源 generation/offset |
| 原有接口 | 返回形状、解码和 SQL 大部分可复用；需适配后端 | 可继续读明文镜像，但发布与缓存失效仍要处理 |
| 源目录零辅助写入 | 普通只读连接不能默认保证 | 原始文件字节读取可做到，但缺少引擎锁协作 |
| 依赖 | 新增可信 SQLCipher 原生分发及版本回归 | 可沿用 Python crypto，但自己承担数据库协议复杂性 |
| 目前证据 | 真实直读与 WAL 新消息通过，合成并发/Reset 通过 | 全量快照已有验证；完整增量镜像仍未实现 |

对本项目以聊天查询为中心的目标，A 的主要代价是原生依赖、启动派生成本与后端适配；B 的主要风险是需要自行承担数据库一致性与持久化协议。优先正确性、可靠性和维护复杂度，选择 A 更有依据。

## 8. 重启、断点与异常处理的建议

### 8.1 推荐路线 A 的恢复语义

**设计建议，未实现：** 独立保存版本化的来源状态：账号选择、数据根目录、数据库相对路径/文件身份、salt 身份、schema 版本、最后成功校验时间、健康状态及离线镜像时间点。采用本地原子文件替换或独立 SQLite 事务存储，不保存聊天正文与密钥到日志。

重启时重新定位并验证来源和密钥，重建短只读连接与内存缓存，直接查询当前已提交状态。没有物理镜像就不需要恢复页 offset；源 Checkpoint/Reset 不构成“漏同步页”。但这**不等于已经满足逐条消费者断点续读**，不能用“保存了最后查询时间”冒充可靠消息游标。

如另行确认需要持续消费新增消息，应先定义本地 sink，再设计 `(账号、来源代次、分片、表、local_id)` 定位、有效 `server_id` 辅助校验、幂等 upsert 与消费状态同事务提交。`server_id=0/NULL` 已在 Phase 1 发现；只有 `local_id > max` 会漏掉旧行更新/删除，不能宣称完整状态同步。限定回看窗口只能降低风险，不能证明任意旧消息修改必达。

两条路线都不能凭空恢复已经从本地数据中删除、且日志也已回收的中间事件。先保证当前持久化聊天状态正确，若要求永久事件审计，应另定范围。

| 异常 | 建议行为（待实现和验收） |
|---|---|
| BUSY、LOCKED、短暂文件不可读 | 短超时、有界退避后重开；完整操作失败时不发布半份成功结果 |
| 微信退出或侧文件消失 | 关闭旧读会话，重新核验当前主库；不创建替代聊天库 |
| 源文件替换、salt/key 改变 | 使派生缓存与通知连接失效，重新验证；错误密钥明确报错 |
| 账号切换 | 固定用户选择与密钥校验，不自动读到另一账号 |
| 状态文件损坏 | 隔离坏状态并重新发现，不能将可疑状态作为成功进度 |
| 当前源无法安全读取 | 明确错误；若用户选用离线镜像，明确其时间点与非实时状态 |
| 全量恢复 | 用户可调用已有流程，结果通过关键库检查后才作为有效镜像；不能静默每轮全量解密 |

### 8.2 为什么不选择其他“省事替代”

- 周期性全量解密：已知本机单次约 14.32 秒，且成本随 D 增长，不符合日常增量目标。
- 每次用 backup/export 重新生成明文库：可用于一次性一致快照，不是可持久续传的变更日志。SQLite backup 在其他连接改源时可能重新开始复制，不能按“每次复制几页”就宣称跨轮次增量；SQLCipher 跨密钥备份能力也需单独验证。[SQLite Backup API](https://www.sqlite.org/c3ref/backup_finish.html)。
- 文件监控事件、mtime 或 WAL 长度：只能作唤醒/优化提示；不能替代事务边界，尤其存在物理长度不变的 Reset。
- 把 `immutable=1` 用于在线库、禁用锁、修改微信源以加触发器：不采用。

## 9. Phase 2.2 的具体实现计划（等待确认）

以下仅为计划，不是本阶段已交付功能。

### 步骤 1：确认范围与依赖门槛

- 确认实时接口直读、不维持实时物理镜像，以及 SHM 协调边界。
- 固定经验证的 SQLCipher 绑定/引擎版本，检测缺失依赖和 codec；继续保留原 Windows 明文后端作为显式选项。
- 先完成下节真实多进程稳定性、权限和资源实验；失败时回到路线评审，不直接进入自研 WAL 复制。

### 步骤 2：最小原生只读后端

- 新增独立的 native reader 模块，负责密钥装载与内存派生缓存、参数初始化、只读连接、短事务、字典行结果、流式游标与错误分类。
- 在 `config.py` / `db.py` 作必要的薄适配：选择源后端、定位账号和分片、实现 `query/query_raw/iter_query`；保持现有函数参数、结果和 MCP 工具形状。
- 避免每个 SELECT 重做 PBKDF2。连接按请求短开或使用受控池；不能跨线程无锁共享 Connection，生成器必须可靠释放资源。先用测得的成本决定池的必要性。
- 不迁移源库、不改源 journal mode，不默认加载第三方 FTS tokenizer；普通聊天查询沿用现有 SQL 与消息解码。

### 步骤 3：变化感知、缓存与持久化恢复状态

- 常驻模式以 0.5–1 秒检查同连接 `data_version`，用于健康与缓存失效；消息查询本身仍从源当前事务读取。
- 定期轻量发现新增/删除/替换的 `message_N.db`，覆盖多位数字分片；检测账号/salt/文件身份变化并重开。
- 联系人缓存随联系人库变化失效；重新发现 schema/Name2Id，不为每个群启动一套解密任务。
- 持久化来源/健康状态并完成损坏恢复。是否追加逐条消费 sink 和逻辑游标，按第 8 节范围另行确认，不能假借 data_version 实现。

### 步骤 4：故障处理、兼容性与交付

- 做有界重试、显式离线状态、关键库检查与恢复指引；不自动切换账号、不把旧镜像当作最新查询结果。
- 原合成测试全部回归，新增后端、线程/游标清理、变化感知、缓存、路径替换与状态恢复测试。
- 用下面的真实矩阵完成验收，再更新使用说明；长期压力与全量比对继续进入 Phase 3。

原来的 `decrypt_stream.py` 缺陷可单独提交修复及回归测试，但不应成为本路线实现的必要前置，也不在本阶段顺带改动。
